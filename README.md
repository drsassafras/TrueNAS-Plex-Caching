# Plex Cache for TrueNAS

**Superspeed your HDD-based Plex server.**

Plex Cache is a small app for TrueNAS that keeps the parts of your Plex library you're about to watch or listen to in ZFS's caches — RAM (ARC) and SSD (L2ARC) — so playback starts, seeks and moves on to the next episode or track at cache speed instead of waiting for hard drives.

Everything is set up in a web UI: what to cache, how much, and when. Health checks tell you whether your system is set up to benefit — with the exact command to fix anything that isn't — and the Metrics page shows whether it's actually working.

## Features

The web UI has nine pages: **Health**, **Caching** (what gets cached and how much RAM it may use), **SSD Cache** (your L2ARC and how big it needs to be), **Library** (what's where in each file and what caching keeps of it; the content checks), **Tools** (the optimizer, converting to MKV, a folder made a dataset, and tools for the library itself: Merge Duplicates, Duplicate Versions, Organize Folders, Sync Libraries…), **Processes** (what each job did, file by file), **Mirror** (another Plex server with the same files, and what Plex's own sync carries between the two), **Metrics** and **System** (connections, access, media mappings, disk speed, MQTT, updates).

### L2ARC or RAM only

Caching is planned around an SSD cache (L2ARC) on the media pool, and Health warns when there isn't one. To run on RAM only, tick **I won't use an L2ARC** on the SSD Cache page. Dropdowns start with an explicit **Default** choice that names what it means right now (e.g. *Default — At 90%*), and mark the other choices: a green RAM icon on the default used without an L2ARC, a blue SSD icon on the default used with one, a grey SSD icon on L2ARC options (they fall back to the RAM default without an L2ARC), and a grey RAM icon on RAM options (ignored when there's an L2ARC). The same icons sit beside settings that are wholly one kind, and a legend at the top of the Caching page explains them. Defaults are looked up every time caching runs, so they change by themselves when an L2ARC is added or lost. A choice that needs an L2ARC falls back to its RAM-only default when there isn't one, and Health lists any setting that had to fall back.

### Three caches, one page each

The Caching page has a card for each cache, with each library's choices on it, and help behind "How it works".

- **Now Playing Cache** — once a stream is playing and Plex's own buffer has had time to fill, reads the file being played into RAM from the play position onwards, then the beginning, so skips land in cache.
  - Start timing worked out from the file's bitrate and your disks' measured speed (direct play and transcoding buffer differently), or a fixed delay.
  - The whole file if it fits its RAM limit, otherwise as much as fits ahead of the viewer — and it starts again from the new spot after a big skip.
  - Reads a set number of files at a time, so hard drives aren't asked to seek between many streams at once.
- **Lead-in Cache** — a file's *lead-in* is its first seconds plus its seek index: everything a player needs to start it instantly. Per library: the lead-in length, a warm-up schedule, and how far Prefetch reaches.
  - **Warm-up** (needs an SSD cache, L2ARC) puts the lead-in of every movie, episode and track in a library on the SSD: at boot only, or at boot plus twice monthly (the 1st and 15th), weekly, twice weekly (the chosen day and three days later) or daily, at one shared time — or not at all, with "Run Now" for any time. There's no on/off switch: warm-up runs for every library that has a schedule. Default follows the caching mode: at boot only with an L2ARC, no warm-up without one.
  - **Prefetch**, once Now Playing Cache is done, loads the lead-ins of what's likely to play next, in Plex's own order (across seasons and any folder layout): don't prefetch · next episode · rest of the season · whole season · next season · all seasons · the whole library (from "whole season" on, an L2ARC is needed). Music and audiobooks use the same ladder for tracks and chapters, albums and books (music has no "next album"); movies follow their Plex collections.
  - Lead-in length is in seconds of playback (by default 60 for movies, 30 for TV and 10 for audio), scaled by each file's own bitrate, so a 4K remux gets more bytes than a 720p episode. The seek index (MKV Cues, MP4 `moov`) is found from the file's own layout. If your settings don't fit the SSD, lead-ins are shortened automatically.
- **Whole File Cache** — near the end of what's playing (at 80% or 90%), Prefetch loads whole files, per library: nothing · next episode · rest of the season. On RAM only, music's default is nothing: RAM is scarce and tracks are short; with an L2ARC it's the rest of the album, like the others. Episodes already watched aren't offered in full: they'd only push lead-ins off the SSD.
- Each Prefetch step includes the ones before it, read in order, so the next episode always comes first. The season is that of what plays next: at the last episode of season 1, "rest of the season" means season 2.
- **Needed soon → RAM, needed later → SSD.** RAM keeps one-off reads for hours at most, so only the next episode in full and the rest of the season's lead-ins are read straight into it. Everything further ahead — earlier episodes' and the next season's lead-ins, all seasons, the whole library, the rest of the season in full — needs an L2ARC and goes to the SSD in the background, at the L2ARC pacing and outside the RAM limit; without one it falls back to the RAM default. Each choice in the dropdowns says which way it's read. Defaults follow the caching mode (with an L2ARC: lead-ins of the whole library and the rest of the season in full; on RAM only: the rest of the season's lead-ins and the next episode in full).

### Cache Settings and RAM Only Settings

- **RAM limits that respect your NAS** — Now Playing Cache and Prefetch each get a share of the ZFS cache that's actually available (never more than its maximum), minus a reserve left for the rest of the NAS. They cover what's meant to stay in RAM — Now Playing Cache and whole files, and without an L2ARC lead-ins too — with or without an L2ARC. With one, lead-ins only pass through RAM on their way to the SSD (that's how ZFS fills an L2ARC), so they don't count; the L2ARC pacing keeps them gentle.
- **Cooldown** — everything cached is logged, lead-ins in one log and whole files in another, and isn't read again until its cooldown has passed, whichever feature asks. A whole file counts as a lead-in too, so warm-up skips files Prefetch just read, and Now Playing Cache doesn't re-read a file Prefetch loaded near the end of the last one. RAM keeps one-off reads for hours at most, so on RAM only the cooldowns in RAM Only Settings apply (2 hours for lead-ins and 3 for whole files, by default; from none or 10 minutes up); with an L2ARC everything read is taken to be on the SSD, and the L2ARC cooldowns on the SSD Cache page apply instead (1 day for lead-ins and 6 hours for whole files). Timed warm-ups only skip lead-ins Prefetch cached since the last warm-up, so they always re-check their own — what's still on the SSD is a quick hit, and what the L2ARC has since overwritten (it reuses its space oldest first) is read again; "Run now" reads everything.

### L2ARC Cache Settings: big jobs in the background

On the SSD Cache page. Everything that needs an L2ARC — warm-up, and the Prefetch choices with the grey SSD icon (all seasons, the whole library, the rest of a season in full...) — reads in the background at the L2ARC pacing. By default that's just under how fast ZFS copies to the SSD (`l2arc_write_max`): anything read from the disks faster leaves RAM before it's copied, while reads that come from the SSD already aren't held back. It also steps aside, then carries on from the same file, while a player is buffering, while Now Playing Cache or Prefetch is reading for someone, during a scrub or resilver, or when the disks are busy with other work. Caching that works on RAM alone — Now Playing Cache, and Prefetch's smaller steps like the next episode — never waits, so the reads that help most always happen, while large ones can't get in the way. Prefetch's L2ARC-only reads share one queue for every player: the newest request goes to the front (after the file being read finishes), and everything in it is read in the end, even after its player stops.

### Health checks that explain themselves

- **Plex and TrueNAS** — server reachable, signed in, API key accepted. The TrueNAS connection is read-only.
- **Libraries** — opens a real file in every library folder, and suggests the right folder when the app has it mounted somewhere else. Each library also shows the record size of its dataset (always read from the dataset: from TrueNAS, or from ZFS itself) and the one recommended for it from its average bitrate: 512K under 1 Mbps (music, audiobooks), 1M up to 15 Mbps (FLAC, SD to 1080p encodes), 2M up to 40 Mbps (4K encodes, 1080p remuxes), 4M above (4K remuxes), and 128K for files under 1 MB. A second best is named too, the neighbouring size on the side the bitrate leans to. **Ideal** when the dataset uses the recommended size, **Pass** when it uses the second best (fine too, so a library near the line between two sizes doesn't flip between them), **Warning** otherwise; the column's ⓘ says where to change it in TrueNAS.
- **Media Datasets** — for every dataset a library is on, one column per check, each with an ⓘ saying what it checks, why it matters and what to do about a warning:
  - **Cache settings** — `primarycache` and `secondarycache`;
  - **Dataset record size** — that the setting suits every library on it (each library's recommended size or second best). When no one size can, it names the library to move to a dataset of its own, since a record size is set per dataset;
  - **File record size** — that every file is written in that size (**All files match**). A new record size only applies to files written afterwards; every health check looks at every file (one `stat()` each, a fraction of a second for 20,000 files), and the [optimizer](#the-optimizer-files-written-for-caching) writes the others again;
  - **Compression** — ZSTD at levels 3 to 19 passes; ZSTD-3 (plain "ZSTD" in TrueNAS) is recommended. From level 3, ZFS gives up early on what won't compress (most of a video), so higher levels only make marginally smaller files for more CPU when writing — reading is no slower at any level — and on a mostly idle NAS that's your call. ZSTD-1 and 2 (slightly less compression, no faster in practice), LZ4, ZSTD-FAST and anything else get a warning;
  - **L2ARC** — the SSD cache on its pool.

  Also flags datasets mounted in the app that no library uses, and works out which dataset really holds a library when datasets are mounted inside one another.
- **ZFS and RAM** — how much RAM is free for preloading, and whether ZFS settings would stop warm-up from landing on the SSD (for example, warm-up reading faster than ZFS copies to the SSD).
- **Is It Working?** — compares warm-up runs to show how much was already cached, and a day after each run checks a sample of its lead-ins: how many are still on the SSD. The L2ARC reuses its space oldest first, so that's how long lead-ins really last on your NAS.
- Every problem comes with the fix — a setting to change or a command to copy — and features that can't work on your system are switched off with the reason, coming back on by themselves once it's fixed.

### The optimizer: files written for caching

A second container, `plex-cache-optimizer`, rewrites media files so they suit caching. It's optional, and the only part of the app that writes media. It does nothing on its own: on the **Optimizer** page, choose for each library what it should do — each library is a section of its own, its choices at the top and a card under them for each file there's something to do to (the file as it is now, its warnings in yellow, and as optimizing leaves it, each setting Ideal or Pass) — then tick the files (**All** ticks every one, on every page) and press **Optimize Selected**. Until it works, the top of the Optimizer page checks, in order, everything it needs — in the app's YAML, running, answering, holding the app's token, with its tools, with media it may write — and shows only what's left to do, with the lines to paste filled in for your NAS. With a TrueNAS API key that can see apps, it can tell "not in the YAML" from "stopped right after starting". Health → Plex Cache says in one line whether it's ready.

Per library:

- **TrueNAS compression & record size** (on by default) — writes each file again, byte for byte, so it takes its dataset's current record size and compression: ZFS applies both only to files as they're written. Any kind of file. The copy is read back and must have the same SHA-256 as the original before it replaces it. A file's compression can't be read back from it, so Plex Cache keeps a record of its own (below); the record size is read from each file.
- **Optimize MKV files** (off by default) — for each MKV file it:
  - remuxes it with MKVToolNix (`mkvmerge --no-attachments`), keeping every track as it is — image subtitles (PGS, VobSub) get zlib, mkvmerge's default; video, audio and text subtitles aren't compressed;
  - handles cover art (image attachments, which some DLNA players and TVs show) as the library chooses with **Cover art**:
    - **Plex poster, unmatched items only** (the default) — when Plex can't match something to an online entry (home videos, concerts, rare releases), it has nowhere to fetch artwork from again, and the most reliable place to keep it is in the file. Those get Plex's poster (whatever you set in Plex), losslessly compressed as below; matched items have their cover art taken out, since Plex fetches it anyway. Plex marks unmatched items with a `local://` guid;
    - **Strip it** — takes it out of every file;
    - **Keep it, compressed** — keeps it, losslessly compressed: PNG with [oxipng](https://github.com/shssoichiro/oxipng) (`-o 4 --strip safe`, which keeps colour profiles and transparency), JPEG with jpegtran from libjpeg-turbo (`-copy all -optimize`: new Huffman tables, the picture and every marker untouched, still baseline JPEG so every TV shows it). Each result is decoded and compared with the original pixel for pixel, and kept only if it's smaller;
    - **Plex poster, every item** — puts Plex's poster in every file (a movie's own; an episode's season poster, or the show's), as `cover.jpg` or `cover.png`, losslessly compressed the same way. The app downloads the poster as Plex has it (not resized), and rewrites the file again when the poster in Plex changes;
  - handles the file's tags (titles, notes, and the statistics MKVToolNix writes for each track — Plex reads none of them) as the library chooses with **Tags**:
    - **Keep tags** (the default) — nothing is lost: ffprobe, Jellyfin and MediaInfo keep the track durations and bitrates they read from the statistics tags, and home videos Plex can't match keep their titles and notes. Usually a few KB, but some tools write hundreds of KB, cached with every file;
    - **Strip excessive tags** — only files with over 256 KB of tags (the ones Library Health warns of) lose them;
    - **Strip tags** — every file loses its tags, global and track (and no new statistics tags are written): the least metadata to cache, but other players show less. Plex is unaffected.

    The optimizer's own tag is always written back, whichever is chosen;
  - puts the attachments back **after the video** (`mkvpropedit`), least compressible first — images, then fonts, then text — and moves the index and tags after them. The lead-in is then all video, and everything that compresses sits together at the end of the file, next to the padding of its last record;
  - writes it in the dataset's current record size and compression;
  - checks, with ffmpeg, that every video, audio and subtitle stream is exactly the same as before, and every attachment is byte for byte what was meant to go in.

A running job shows on the Optimizer page (and on Health) with a progress bar, the file in hand and an estimate of when it'll be done (from how fast files are really written on your NAS), with **Pause** and **Cancel** (both after the file in hand). It pauses by itself while the pool is resilvering — that pause can't be lifted by hand — and starts paused if a resilver is running. Its progress is saved after every file, so a restart carries on where it was ("Optimization Resumed"); a file the optimizer was in the middle of is simply done again (the original is only ever replaced whole). Only one file activity runs at a time: optimizing, syncing cover art, or moving a folder to its own dataset.

Either way it works one file at a time, skips anything playing and anything written in the last 10 minutes (still being imported), keeps each file's owner, permissions, timestamps and extended attributes (and skips files whose owner it can't keep), and swaps the new file in with an atomic rename.

**Two kinds of record**, because the two kinds of optimizing last differently:

- **The ZFS record** is about this NAS: a file synced elsewhere is written again there. Plex Cache keeps it in its config folder (`zfs-record.json`): each dataset's record size and compression, and since when they've been seen (the date the record began, then the date of each change, with the earlier settings); and each file's compression, which can't be read from the file:
  - **Optimal** — the optimizer wrote it, with the dataset's compression now;
  - **Assumed** — it first showed up at a check when the dataset's settings were the same as at the check before, so it was written with them;
  - **Unknown** — it was there when the record began, or showed up right after the settings changed;
  - **NotOptimal** — it's known to be written with another compression.

  Optimal and Assumed need nothing; Unknown and NotOptimal are written again. A file written with ZSTD 3 to 19 is never NotOptimal, whatever level the dataset uses now, so changing between those levels never rewrites a library. The exact compression each file was written with is kept either way. Datasets and files gone for six months are dropped.
- **The MKV record travels with the file**: the optimizer tags every file it optimizes (`PLEXCACHE_OPTIMIZER` = its version, a global Matroska tag; the file's own tags are kept), so a file copied, migrated or synced to another system isn't done again there. The optimizer has its own version, **0.1.2**: a new minor version (0.2) means files are done again, a new patch version (0.1.1) doesn't, and a file tagged by a newer optimizer is never touched by an older one. Plex Cache remembers each file's tag with its size, modification time and inode, so it reads a file's tag once; after that, telling what's done is one `stat()` per file.

**Convert to MKV** is a tool like the others (Tools → Convert to MKV): its scan lists every video file in another container, and its switches per kind, per library, say which are live — AVI, MPEG-TS/M2TS, MPEG-PS (VOB, MPG), FLV, OGM/OGV, RealMedia and 3GP on by default; MP4/M4V and MOV off, shown grey, until you switch them on (Apple's apps and some TVs play them directly, and they can hold iTunes details MKV doesn't keep) — and Apply converts the ones you tick as a process: the backup first, per the Backup preference, then each file, with the run in the tool's history and on the Processes page. Music and audiobooks are never converted; the optimizer's own runs never convert.

- **Inspected first.** What MKVToolNix reads of the file (`mkvmerge -J`) is compared with everything ffprobe sees in it. If anything wouldn't be kept — a track MKV can't hold (Teletext, an MP4 closed-caption track), chapters, cover art, details such as an iTunes show and episode — or it's protected by DRM, the file is left as it is, its row in the run failing with the reason; the next scan lists the file flagged *Left as it is* with that reason, and it isn't tried again unless it changes (or you tick it again).
- **Checked after.** The MKV must hold every video and audio track with the same codec and number of packets, every subtitle track (MP4 text subtitles become SRT), and any closed captions inside the video. Then it's optimized like any MKV, and given the original's owner, permissions and timestamps.
- **Plex keeps its metadata.** The MKV is written next to the original (`<name>.mkv`, never over an existing file) and Plex is asked to scan that folder, so it adds the MKV as a second version of the same item, even when libraries are scanned by hand. Once Plex has it — on the mirrored server too, where one is watched — the original is deleted and the folder scanned again; there is no hold, since the run's backup holds the original. The item keeps its edits, watch history and collections. If Plex makes the MKV an item of its own, nothing is deleted: merge the two in Plex and it carries on, or choose **Keep Both**. The converted files on their way into Plex are listed under the tool's runs, with **Check Again** and **Delete Original Now** (for an original that couldn't go yet: it was playing, say).
- **The way back.** Revert on the run removes the MKVs and, where an original has gone already, puts it back from the run's snapshot; Roll Back Whole Snapshot is there too, like any tool's run.
- **A second Plex server** with the same files (another site, synced) can be watched too, on the **Mirror** page (Second Plex Server). Choose it from your Plex account's servers — the sign-in this server already has lists them; **Use Another Plex Account** is for a server on another account — (its addresses are tried, direct ones first; at another site it needs Remote Access, or a VPN), and check how each library is paired with one there (by name and kind unless you choose). A file's path there is its place in its library folder, under that library's folders there, and the page shows what share of each library's files were found that way. An original is then deleted only once both servers have the MKV as a version of the same item — or the other doesn't have the file at all, which counts only when the paths line up (90% of the library's files found), never on a guess. Its folder there is scanned too.

**Library Health** (the Library page's **Health** view) checks the content itself, apart from caching, in two kinds — each check with its own switch:

- **File checks**, on the files as inspected: no audio track; a spoken-language film with no subtitles (a file whose audio is marked `zxx`, no linguistic content, isn't flagged); subtitles on a `zxx` film that aren't forced ones (forced subtitles carry written content and belong; others are probably for another film); **Forced Subtitles Without Their Audio** — a forced track in a language none of the audio tracks is in (forced subtitles are written in the language of the audio they go with, for foreign speech, words to read before they're heard, and text on screen; a forced German track without German audio was most likely made for a German-dubbed version that isn't in the file), flagged too when the audio's language is unknown; **Audio Language Unknown** — an audio track tagged `und`, or with no language tag at all (every Matroska player takes an untagged track for English and picks it as such, so it's right only if it is; `zxx`, no linguistic content, is fine). The subtitle check can be narrowed with two options under it, off until you turn them on: **Must include the chosen language** (picked beside it, from the languages the library's files hold; English by default) and **Must include SRT or ASS** (a text format, not only bitmap ones like PGS or VobSub); with both, that language's subtitle must be the text one.
- **Audio checks**, for music and audiobook libraries only: a lossy track below its codec's floor at the quality level you pick beside the check (every codec's floor scales alike — MP3 needs the most, Opus the least; as it ships, *Only clearly poor* flags MP3 under 128 kbps stereo, AAC under 88, Opus under 64; *Fair*, *Good* and *Transparent* raise the bar; lossless codecs never), **Outdated Audio Codec** (off unless you turn it on, with the Hydrogenaudio listening tests linked from its ⓘ): a track in a codec that today's beat at any bitrate — MP3, MPEG Layer II, WMA, RealAudio, and in music libraries AC-3 — each finding saying what the codec is and where it falls short, **Audio Safely Compressed**: audio FLAC would hold bit for bit in less space — PCM, WAV, AIFF or a Blu-ray rip's LPCM track (about half); in a video a DTS-HD Master Audio track (a tenth or so); and a DTS track judged per track from the bitrate Plex read against what FLAC would need for its channels and bit depth (a 1.5 Mbps stereo track shrinks to about 0.9 Mbps and is flagged; a 5.1 track at the same bitrate would double and isn't) — TrueHD comes out the same size and the other lossy tracks bigger, so neither is flagged, and Dolby Atmos and DTS:X tracks (named so, or 7.1) are left alone, since their object metadata doesn't survive re-encoding; and **Audio Compatibility**, for videos: a track in a format most Plex clients can't play as it is — TrueHD, DTS-HD MA, DTS, Apple Lossless, PCM — where a FLAC version would play everywhere at about the same size or less. Plex transcodes such audio to lossy AAC or AC-3 unless the client or a receiver decodes it, so a lossless track that can't be played is heard lossy; FLAC is decoded by every current client. The ⓘ weighs the gains against legacy receivers that decode DTS or TrueHD themselves. The last three look at a video's audio tracks as well, joined to the streams Plex probed (the data layer reads each item's page for them).
- **Plex checks**, on how Plex has each item: versions (several files on one item) whose file names carry different titles or years — a version added to the wrong item, most likely; versions whose running times differ by more than a little (3% or two minutes, whichever is more); a field you locked that holds nothing (**Empty field locked**). The locked-field check needs each item's own page: the pages are read after the records, and again as items change.

The Plex checks also run on both servers' items in Sync Libraries: a record that fails one is tagged **Looks wrong** — the data is likely bad on that side, worth a look before applying.

**The Mirror page** is where a mirrored server is set up — another Plex server with the same files, at another site, kept in step by syncing the folders — with what Plex's own sync carries between the two (**Watched State**: Plex's "Sync my watch state and ratings"), and what uses the mirror: Convert to MKV, Sync Libraries and Mirror Checks.

- **Mirrored server** is a choice to make: *Not chosen yet* (the default: Health asks, and converted files' originals aren't deleted, since a mirror that isn't watched could lose its item), *None*, or *Yes*, the server watched. **Look for mirrors** checks your Plex account's other servers, weekly and when the Mirror page opens: a sample of each server's files is looked up here by path, and a server with nearly all of them here "looks like a mirror" — a click watches it. Another Plex Cache sharing the folders is noticed by the marker it leaves there (the optimizer's claims).

**Sync Libraries** (Tools) makes a library on the mirrored server the same as here, or here the same as there — one way, from the side whose edits win, through the other side's Plex API. It's a tool like the others: the same page, cards, Apply, backup and Revert, and it runs only when you press Apply.

- **What it compares**: each paired library on both servers, read through the data layer like every tool's (for each item that differs, its own page from both servers: Plex's listings don't say which fields were edited). Items are matched by their files' place in the library folder (the same on both), falling back to the online entry; shows, seasons, artists and albums through their episodes and tracks. Items sharing files across the two servers form one row: a pair; one item on the winning side that's several on the other (applying merges them there); an item the other side doesn't list (its folder is scanned there). The differences, by kind: a file the other side doesn't list, versions grouped differently, another match (or unmatched on one side), edited fields (Plex locks a field you edit), posters and backgrounds chosen by hand, collections, labels, and editions. Watched state and ratings aren't compared: Plex's own sync carries them. An item only on the other side is left as it is: nothing is deleted.
- **Its options**, per library like every tool's, sit at the top of the page, each with the count of rows it covers: **Whose edits win** (this server, or the mirror: changed, the rows turn round over the same data, nothing read again), **Files the other side doesn't list**, **Versions grouped differently**, **Matches**, **Edited fields**, **Posters chosen by hand**, **Collections and labels**, **Editions**.
- **Each row** is the comparison card: the other side as it is now, and after syncing, with yellow checks for what will be done and grey notes: **Would lose metadata** (the winning side's copy unmatched with no description while the other's is filled in: a sign the wrong side's edits are winning), **Edits undone there** (a field edited only on the other side is unlocked and given the winning side's value), **Looks wrong**.
- **Applying**: tick rows and press **Apply**. Each is made true on the other side: edited fields set and locked as the winning side has them (and edited tag fields: genres, directors…), the match, a poster or background chosen by hand (its image uploaded), collections, labels, the edition, versions merged into one item, and the folders of files it doesn't list scanned. Nothing is deleted. The records it will change are backed up first (the Backup preference), and **Revert** puts them back; without that backup (*A backup I make myself*), what each row had before is put back instead — the fields (unlocked again if they weren't locked), the match, the poster chosen before, collections and labels — though a merge can't be.
- **What it can't do is Mirror Checks'**: several items on the winning side that are one on the other (that needs a split), files shared out among items differently on both sides (**Grouped differently on the mirror**), and a file that isn't on disk at the other site.
- **What stops a row** is a red tag on it, until it's put right or ignored: Mirror Checks finding the item's files aren't the same at the two sites (on one side only, a different size, in Plex here but not on disk: the two sides are paired by their files, so syncing it could bring the wrong item in line), Plex Checks finding a file on its record that looks like another film's (**Dissimilar file versions**), or its record one of a film's several (**More than 1 Plex record**: merge them first). Mirror Checks and Merge Duplicates are worked out before Sync Libraries, so the tags are in place before its count shows. The whole library is held while `.plexcache` doesn't reach the other site.

**Three tools for the library itself** (the Tools page) each scan a library, show what they would do, and do only the rows you tick, one at a time, with every step logged. Files are only ever touched through the optimizer service — the one part of Plex Cache that may write to your media — and Plex is asked through its API, here and on a mirrored server where that matters.

**Every tool's row is the same comparison card** — Merge Duplicates' look, for every tool and for each file on the Optimizer page: what goes framed in red and labelled, what stays or comes framed in green, the arrow between them (a button where you choose which side stays — Merge Duplicates, Duplicate Versions — fixed where nothing but the backup turns it back: Organize Folders, Convert to MKV, Unlink Files, the Optimizer), grey **File 1, File 2…** chips that open to what happens to each file, and the files listed under it, numbered the same. Each tool passes only its own labels: *Metadata kept / lost*, *This file kept / deleted*, *Original folder / Folder moved here*, *Original file deleted / New MKV created*, *File kept / This hardlink deleted* (or *Hardlink replaced with file*, *Symlink replaced with file*), *File as it is now / File after optimizing*. Long lists come a page at a time; **All** ticks every row that can be ticked on every page, **This page** the ones on the page open. The colours of the checks on a card mean the same everywhere: **yellow** is what there is to do — a row with one can be ticked; **red** stops it — a row with one can't be ticked, and the server won't do it either (a record it would destroy, a record still to merge); **grey** says something worth knowing and changes nothing. A tool's page shows only the rows with a yellow or a red check, and File Checks and Plex Checks only the items they flag; the Library page shows every item. **Red reaches the Tools page.** Whatever is red on a tool's page because it stops part of the tool — a row a red check stops, the optimizer not set up yet, checks a check page couldn't run — turns that library's tab, the tool's card on the Tools page and the count beside Tools in the menu red too, a red 0 included, the same way for every tool (the server says which libraries, `tools_red` in the state, and one function on the page reads it). With nothing red, a count is yellow when there's something to do and green at 0.

**What stops a row, and the two ways out.** A red tag that stops a row — on every tool, Sync Libraries' included — opens to the same four parts: why it's stopped and which page found it, what could go wrong if it went ahead anyway (said for that tool), how to put it right (an example), and **Ignore**. Going ahead is still possible, so it's yours to choose: Ignore, there or on the page that found it, greys the tag on that record and frees the row at once, with no scan again; **Bring Back** on the grey tag stops it again. Every block a tool's rows can carry has these words (`Tool.block_ids`, `blockText` in `app.js`), and a test fails on one that doesn't.

**Every number is evaluated before it shows.** Each count a page shows — a library tab, a card on the Tools page, the count beside Tools in the menu, a line on the Library page — comes from one place (`plexcache/evaluate.py`) in one of four states, and the page draws every one of them with one function: *done*, the number; *pending*, a turning wheel and, where the results go, what it's waiting for and how far it's got — never a number, not even 0; *doesn't apply*, a grey dash and why (a tool that doesn't work on that kind of library, Sync Libraries or Mirror Checks on a library that isn't paired with one on a mirror, the optimizer with neither rewrite chosen): what setting it up would show, not a result; *couldn't be worked out*, a red !, with why. A count that grows as it's read — File Checks while the inspector reads the files, Plex Checks while the items' pages are read — shows what's been found so far beside the wheel (*N found so far — still counting*), with those items listed under it, coloured as a finished count would be — red when something red has been found, yellow with something to do, grey (never green) while nothing is. A page's total, and the menu's, is a number only once every library it applies to is in; until then it shows what's in so far beside the wheel — the libraries done, and what the rest have found so far. Nothing is said before it's known: with a mirror watched, Mirror Checks says it's reading the mirror's libraries (or that the mirror couldn't be reached), never that no mirror is watched, until it knows which libraries are paired. A page shows one progress bar, the placeholder's, a scan running included. A count worked out again — a check page after a restart, Mirror Checks scanning again — shows what it found last time beside the wheel (*N found last time — checking again*) with those findings listed, updated when the new ones are in; meanwhile the buttons on those findings (Scan Folder, Ignore, Bring Back) are disabled, and refused by the server, until the scan is done. A mirror that can't be reached is never taken for one with nothing paired: what was read of it is kept. **One queue, the page you're on first.** Everything counted per library — its data read, Mirror Checks, every tool's scan, File, Plex and Mirror Checks, the optimizer's scan — is worked out in the background by one queue, in the order the page open needs it: its library first, with what it waits for before it (the library's data, then Mirror Checks and Merge Duplicates, whose findings put the red tags on other tools' rows), then the page's other libraries, then everything else; the rest pauses meanwhile and picks up where it was. The file inspector is steered the same way. **What's worked out is kept.** What the inspector reads of each file is saved, and a file is read again only when it changes on disk, when an update reads more of each file (File Checks' count waits meanwhile, what was found so far shown), or after 30 days. Each tool and check is worked out again when what it reads changes, when an update adds to what it checks, or after a stale period of its own (a day for the tools, Library Health and the optimizer's scan; 6 hours for Mirror Checks), its count standing meanwhile. The tests hold every page of the Tools menu, present and future, to this.

- **Merge Duplicates** finds the same film (or show) on several Plex records — the same match, or, unmatched, files named for the same title and year — and makes them versions of one with Plex's own Merge, which keeps the record's metadata: its edits, poster, collections and watched state. Records matched to one entry but titled apart are left apart on purpose (a work released in parts, Henry IV Part 1 and Part 2, each its own record), as are different editions and recordings of different lengths, unless two records hold the very same file (a link or a copy: the same size and running time), which makes them one film whatever they're matched to. The record kept is the one with the most edited fields, then the most files, then the oldest. Only this server's Plex records change: no file is touched, so the folder sync carries nothing and a mirrored server keeps its own records. With the mirror watched and this server's edits winning in Sync Libraries, it merges them there too (scanned again, the film shows as one item here and several there; applying it merges them); with the mirror's edits winning, merge on the mirror instead and let Sync Libraries merge here; a mirror that isn't watched needs Merge Duplicates run there. The box before Apply says which applies.
- **Duplicate Versions** finds one Plex record holding the same file twice — the same size and running time, and the same bytes at both ends (over thousands of files two merely alike in size and length do turn up): a copy that slipped in, or a second path to one file (a link, said so). The copy kept is the one in a folder of its own, then the newest, then the first Plex lists — or the one you choose with the arrow on its card; the others are set aside in the library's own `.plexcache-trash` folder (on the same dataset: a rename, no copying; Plex is told to ignore it) and Plex asked to scan and drop them. A set-aside file is deleted for good only once Plex here no longer lists it — and, with a mirrored server, once its Plex no longer does either (the synced folder carries the change there) — then after the backup length (**System → Preferences**, the days every backup is kept). Until then it can be put back; the page's **Set Aside** list has **Delete Now**, **Put Back** and **Keep Set Aside** for each, and a file that never meets the conditions (the mirror keeps listing it, say) is held and said so on Health after two weeks. A copy that's the only file of its Plex record here is marked **Record destroyed**, in red: it can't be done until Merge Duplicates has made it a version of the record kept. One that's the only file of a record on the mirrored server is marked **Record destroyed on** that server, in grey: it can still be done, and that record goes there.
- **Organize Folders** moves loose films (files in the library folder itself) into a folder of their own named as Plex recommends — `Title (Year)`, with `{edition-…}` for an edition and, only when two films share a title and year, `{tmdb-…}` to tell them apart — with their subtitles and artwork. **Clean up folder names too** also renames a film's folder whose name doesn't carry the title and year; a folder you named with both in it is left as it is, as is one holding several films. Plex loses nothing: each file is first given its new path (a hard link: the same file, nothing copied — a plain copy on a file system without them), Plex asked to scan the new folder and, once it lists the new path, the record it made merged into the original (edits, poster and watched state kept); only then is the old path removed and Plex asked to scan again. Doesn't Plex list it within ten minutes, the new paths are removed again and nothing has changed. With a mirrored server, the synced folder carries the change there, and the tool follows it: once the mirror's Plex has the new path under a record of its own, that record is merged into the old one there; not picked up after three days, Health says so. Movie libraries only: TV and music have folder layouts of their own.

**Two Plex Caches, one on each server.** Each marks itself in every library folder it shares (`.plexcache/systems/`, written by the optimizer service and carried over by the folder sync) with the settings that matter to the other side: whose edits win in Sync Libraries on each library, the optimizer choices that change a file's bytes (MKV layout, cover art, tags, converting), and the tools lately run there (Sync Libraries among them). From the other side's marker, each refuses what would fight, and Health says so: running Sync Libraries on a library the same way round as the other side did within the week (both with their own edits winning, or both with the other's: edits would go back and forth, so one side's edits must win on both), optimizing a library whose choices differ on the other side (each would rewrite the other's files for ever), and running Duplicate Versions or Organize Folders within an hour of the other side running one on that library. Without the optimizer service a side publishes nothing, and Health says that too.

**The link between the two, and Mirror Checks.** With a mirrored server watched, Plex Cache looks for the Plex Cache at the mirror's site and talks to it directly (**System → Mirror Plex Cache**, with lights like Plex's and TrueNAS's: found, paired, talking, folder sync, version and clock). It's found from the mirrored Plex server's addresses on port 8642 and the address and port the other side advertises in its marker — or the address set by hand, for another port — and pairs by itself when that's safe: each side has a key pair (Diffie-Hellman, 2048-bit), puts the public half in its marker, and pairs only with a Plex Cache that sits next to the mirrored Plex, answers at one of its addresses (or the one set) and holds the key its marker carried. Where the folder sync leaves out `.plexcache`, **Pair Now** on both sides within 10 minutes pairs them instead; both then show the same fingerprint. From then on every request is signed with the key the two work out (it never travels), timed and never repeated, and only reads: each side's status and a library's list of files. **Unpair** forgets the pairing on both sides and makes a new key; neither pairs again by itself. It's meant for your network, a VPN or Tailscale, never the internet. **Tools → Mirror Checks** is a check page like File Checks and Plex Checks — the same page, the same chips, Ignore and counts, each kind of finding a check that can be turned off — and compares each library paired with one on the mirror, every 6 hours or on **Scan Again**: the two disks file by file (through the other Plex Cache: on one side only, a different size; a file changed in the last hour is left out), what each Plex lists (a file the mirror's Plex doesn't list, one only it lists, a file here Plex doesn't list, one Plex lists that's gone), items grouped differently on the two servers in a way Sync Libraries can't bring in line, and whether `.plexcache` reaches the other site at all. What Sync Libraries brings in line isn't listed: a file the other side's Plex doesn't list, on the side whose edits win, is its to scan for (while its **Files the other side doesn't list** is on). Each finding is a chip on its item; a file Plex here doesn't list, or one only at the other site, is an item of its own. Where `.plexcache` doesn't reach the other site, the claims don't either and the two could optimize the same file: optimizing and the file tools are held in that library until it's fixed, the finding is ignored, or its check is turned off. **Scan Folder**, under a finding's chip, asks the Plex that's missing a file to look at its folder. When a scan couldn't compare the other site's files — a Plex Cache known to be there (found or paired) but the link to it not working — a red chip at the top says so and leads to **System → Mirror Plex Cache**, and the checks that need those files show their counts in red, a red 0 included — and so do the library's tab, the Tools card and the menu's count, since the number leaves them out. With no Plex Cache known at the mirror's site (none found yet, or System → Mirror Plex Cache set to say there's none), those checks simply don't run, and nothing is red. A scan's findings show at once: they're laid over the rest of Library Health's answer as it was, without working the library out again. Health lists a link that needs attention, a library held, and the items that differ.

- **Unlink Files** untangles the hard links and symlinks among a library's media. A hard link is one file under two paths: Plex lists one and ignores the other, so the folder looks to hold a file Plex hasn't got, and a folder sync can't carry the link, so the other site gets two whole copies that drift apart and show up as sync differences; Health warns of them per library. By default each link is made a file of its own under the same path (the bytes copied beside it and swapped in, the dates kept), so nothing disappears anywhere, and Merge Duplicates or Duplicate Versions then tidy the copies the same way on each side. On a library with no mirrored server, **Remove the extra paths instead** removes the paths Plex doesn't list, so the file is where Plex has it and nowhere else (a path is only ever removed while another path still holds the file; a link Plex lists under every path is copied instead, for Merge Duplicates). On a synced library that option is refused: a path removed here would be removed at the other site too by the folder sync, and there it isn't a link but the only copy.

**One copy of each library, read by every check.** The tools and Library Health don't ask Plex or the disk for themselves: a data layer (`plexcache/libdata.py`) keeps one copy per library — Plex's records (films and shows, with their files, running times and edits), every file Plex lists as it is on disk (size, dates, inode, link count, symlink), the media files in the folders that Plex doesn't list, the other paths of hard-linked files, and the folder tree — and each check is a function over that copy, so a scan of fresh data is instant and one gathering serves every tool. The copy is gathered in the background after the first checks, the library you have open first; it's saved, so a restart starts from it. It learns of changes by itself: Plex's change stamp on a library says when to read the records again (its files listed from Plex again with them, so a file Plex added reaches every tool's rows), and a walk that reads only the folders' modification times (they move whenever something is added, removed or renamed) says when to read the files again, every five minutes; Scan Again on a tool reads both afresh; a tool that changed files, and a revert of them, has them read again and scans again by itself, so its rows show what is left to do without a Scan Again. What each tool has found to do is counted on its card on the Tools page and summed beside Tools in the menu — items you've ignored on Library Health left out — and Library Health shows one chip per tool on each item it concerns, opening to what the tool would do and a link to its page; the view lists every item of the library, flagged ones first and the rest marked *Nothing flagged*, says how many have nothing flagged, and flags a folder of the library on its way to a dataset of its own at the top. **File Checks** and **Plex Checks** are tools of their own on the Tools page, each the Health view filtered to its checks, with a card count like the others. Every tool's page is the one standard page (`toolPage` in `app.js`): the title with a one-line blurb; the card's heading with the long explanation behind its ⓘ, never as a paragraph; the top, one layout for every tool and both check pages (`toolTop`): the library tabs, each with the number the tool has found there (a turning wheel while it's still counted), and on their right what the last scan found as chips — what was read (green), the issues found, each item once (yellow), how many pass the current tests (green) and how many would pass all of them, every check on at its strictest (grey), plus what a tool adds (Duplicate Versions: the space freed); under them the library's options, one line each with what it finds on the right, in two columns where there's room; and **Scan Again**, with the scanning state; the rows, a poster and the item's name first and the tool's own columns after — or, with none, a sentence saying so; right before Apply, a box saying what Apply does, what it changes (this server's files or Plex records, and what a mirror sees of it) and the backup made first — every tool must have one (`applies` in its page spec), and a test checks it sits just above the button; Apply, with the backup plan; a row's explanations behind ⓘ buttons too. **Options are per tool and per library.** Each tool declares its options and the library kinds each is for, so a library shows only those; what you set is kept per library (the `tools` settings section). A scan finds everything the tool could do whatever the options say, and each row names the issue it's about; a switch decides whether rows about that issue are live — counted on the card, in the menu and on the tab, flagged on Library Health, and open to Apply — so flicking one takes effect at once over the rows already found, with no scan: live rows come first with their issue chip orange, the rest follow grey with the chip grey, and a grey row can't be ticked. Convert to MKV's switches are its kinds of file; Organize Folders has *Clean up folder names too*; Unlink Files has its two kinds of link and the choice of what to do; Merge Duplicates its three reasons; Duplicate Versions its two. A test holds every tool to this model, and every page to the standard. A test draws every tool page with rows and without and fails on a page off the standard. The tests hold every tool to the layer: a scan that calls Plex or the disk fails one test, a tool that fetches for itself breaks the request budget of one listing per gathering in another, and a third checks that a change the layer sees — a record Plex added, a hard link that appeared — reaches each tool's count and chips with no scan pressed.

**Before anything changes files** — the three file tools (Duplicate Versions, Organize Folders, Unlink Files), **Optimize Selected**, and the dataset copy of Child Dataset — two lights must be green or grey: **Room for it** — the free space on the library's folders against what the action writes (a rewrite: the largest file) and, under a snapshot, what the snapshot keeps of the files it rewrites or deletes until it expires, with a 1 GB margin kept — and **Backup**, the plan: what the process does first, per **System → Preferences** (*Backup before files change*). *A snapshot, taken through TrueNAS* (the default where TrueNAS is connected with a key allowed to) is the process's first step, named for what it's for (`plexcache-<tool>-<library>-<time>`, so it's plain in TrueNAS → Datasets → Snapshots) and deleted by the app after the backup days set there (**30** to begin with); *the copies the action keeps* — Duplicate Versions sets files aside in `.plexcache-trash`, Child Dataset sets the old folder aside — are the backup where the action keeps some, and an action that keeps none takes a snapshot; *a backup I make myself* says the process goes ahead without one, and the button says so: **Backup and Apply to … Selected**, or **Apply to … Selected Without Backing Up**. Every tool's Apply runs as a process on the Processes page: the backup first — a snapshot TrueNAS refuses stops it before anything changes, and the page says why — then the rows, one by one, each logged. Every run is a card — the same card on the Processes page and under **History** at the bottom of the tool's own page, which lists that tool's runs; while one runs, the process card from the Processes page (its progress, Pause, Cancel) sits above the history, so the page reads checks, Apply, process, history. A run's files open from the card with the columns common to every run — poster, the item as Plex names it, when, the result as a badge — and the tool's own (each tool declares them: what was done and what was written for Unlink Files; what was set aside and freed for Duplicate Versions; the folder and files for Organize Folders; the records merged and the one kept for Merge Duplicates). The card shows its progress: **Backup created** with the snapshot's name the moment it's taken, before any file changes, then the rows as they're done. Two ways back while the backup lasts, on that card: **Revert Changed Files** puts back only the files the run changed, and **Roll Back Whole Snapshot** (confirmed first) has TrueNAS roll the dataset back to the snapshot — everything written to it since, by anything, is lost. Revert undoes it so: paths Unlink Files removed are made again as links, a link made a file of its own becomes a link again from the path that still holds the file (no snapshot needed), a merge is split apart (Plex's own Split Apart; the folded records' edits don't come back), set-aside copies are put back, a moved film's files return to their old paths, and a link made a file of its own is swapped back from the snapshot. The lights say which plan applies, with a link to change it; a snapshot that TrueNAS wouldn't take stays said beside them until the next one is taken (or it's dismissed), and goes in the log, as every snapshot taken and deleted does. The app speaks both snapshot APIs — `pool.snapshot` on TrueNAS 25.04 and later, `zfs.snapshot` before. Apply, Optimize Selected and Start Copying stay closed, on the page and in the API, until both lights are so.

**Cover art is set once**, when a file is first optimized. A Plex poster already in a file is kept (unless the choice is “Strip it”), and a later change of choice, or a new poster in Plex, doesn't touch optimized files: **Sync Cover Art** does, when you ask. Each Plex poster embedded is tagged `PLEXCACHE_COVER` with the SHA-256 of the poster as Plex has it (before it was compressed), so Sync Cover Art only rewrites files whose poster changed.

**Several systems sharing a library** (Syncthing, both ways) can all optimize it:

- **The same bytes everywhere:** the output is deterministic (`mkvmerge --deterministic`, seeded from the file's content; attachments written by the optimizer itself with their original IDs), so two systems optimizing the same file at once write identical files.
- **Claims:** before remuxing a file, a system claims it — a small file of its own in the library folder (`.plexcache/claims/`); the earliest claim wins, and the others leave the file alone. Claims are made a few files ahead, so they've synced by the time each file's turn comes; a system that never sees another one in the folder doesn't wait. Byte-for-byte rewrites (record size, compression) aren't claimed: they're per NAS, and they keep the modification time, so Syncthing doesn't even notice them.
- **Collisions:** if two systems still change a file at once, Syncthing keeps both (`name.sync-conflict-…`). Optimizing a whole library (**All**) deletes such a copy when it's one of ours — both tagged by the optimizer, every stream and attachment the same — and Health → Plex Cache lists any others for you to look at.

The Optimizer page shows, per library, how many files still need something under its choices, or **Complete**. `python -m plexcache.optimize --check FILE…` checks single MKV files, and `python -m plexcache.optimize FILE…` optimizes them.

**Processes.** A page of its own lists every file job — optimizing, syncing cover art, converting a folder to a child dataset — with the one running now (progress, estimate, **Pause**, **Cancel**) and a log kept six months: each job with when it started, where it picked up after each restart (its resume points), its pauses and why, and how it ended; and each file with how long it took, its size before and after, the verification outcome (passed, failed or not checked), its record size and compression before and after, whether its layout was optimized, and what happened to its cover art (removed, compressed, Plex's poster added…). **Export CSV** and **Export JSON** download it all. A file that fails a check is left as it was; the failures stay listed (and Health says so) until dismissed.

**Convert Folder to Child Dataset.** Health suggests it when one record size can't suit every library on a dataset ("Split dataset"); each library folder is marked *Ideal already*, *Sufficient* or *Split dataset*. A folder can't become a dataset in place, so the Optimizer page walks through it — **Convert Folder to Child Dataset** — and the folder ends up a child dataset at the same path, so Plex and every app see the same files where they were, with their metadata. Plex keeps running; it's restarted once, at the end. The page remembers which step it's at, across restarts.

1. **Create** the dataset next to the folder (`<name>-new`), with the record size and compression shown — in the TrueNAS shell (`sudo zfs create -o recordsize=… -o compression=zstd …`) or the web UI (Datasets → Add Dataset; the page lists the steps). Nothing is copied until it's checked: there, with that record size (or the second best) and a ZSTD 3–19 compression (read through the TrueNAS API), mounted and writable in the optimizer, with room for a second copy.
2. **Copy**: the optimizer copies the folder into it, each file checked (SHA-256, read back), with owners, permissions, times and extended attributes. Pause, resume and stop from the page; it pauses by itself while something plays. Stopped or interrupted, it carries on where it was.
3. **Switch**: a last pass copies what changed meanwhile and compares both copies, file by file; the old folder is moved out of the way (`.<name>.plexcache-old`, undoable); you rename the dataset to the folder's name (`sudo zfs rename …`, or Rename in the web UI where TrueNAS offers it). Turn off Plex's "Empty trash automatically after every scan" until the end, so the files' metadata isn't dropped while they're briefly out of sight.
4. **Verify**: restart Plex; the page checks the folder is the dataset with its settings, every file is there, and Plex shows as many items as before. Then **Delete the Old Copy** (the optimizer can only delete a `.…plexcache-old` folder it made).

It needs the optimizer's media volume to use `propagation: rslave` (in `compose.yaml` and the setup lines), so a dataset made while it runs shows up in it without a restart; the page checks that too. Snapshots keep the old copy's space until they expire.

**With a mirrored server**, the conversion knows about the other site, through the link between the two Plex Caches (System → Mirror Plex Cache) or, without it, the other side's marker in `.plexcache`. Before the copy: the other side must run TrueNAS, said for certain (its TrueNAS API, its kernel or its version file, never guessed from ZFS), and you choose **Convert Both Servers** (the default: the files are the same on both, so the record size that suits them is too; the other side converts its copy once this one is done, with its room for a second copy checked from here) or **Convert This Server Only** (the other side keeps its folder as it is). A child dataset there with another record size is a warning. **The folder sync** is looked at too: with Syncthing's folder (`.stfolder`) at the library folder itself, setting the folder aside stops Syncthing there instead of sending deletes; with it above the library folder, its `.stignore` must leave out `<name>-new` and `.<name>.plexcache-old` (the lines to add are given, and the copy waits until they're there); with no Syncthing found, you say nothing else carries them away. The folder sync is paused here before the old folder is set aside and resumed once the dataset is in place, each said with a button. **A conversion left partway** — at either site — is found and said: here, a folder with a `<name>-new` dataset or a `.<name>.plexcache-old` folder next to it is marked *Partly converted*, with **Pick Up This Conversion** to carry on from the step it's at; there, a warning before the switch and an error from then on (red on the page, the Tools card and Health), until it's completed or reverted there, with the steps for either. While one side switches, the other holds optimizing, the file tools and Sync Libraries on that library (confirmed over the link; said, with only the marker), and once switched Verify compares the files here with the other site's (a file changed in the last hour left out, as it may still be syncing). The page's Mirror column shows each folder as it is at the other site: a child dataset and its record size, a folder, or a conversion under way or left partway.

**Testing it.** `tests/fixtures` holds small MKV files with as many real-world features as practical — H.264 and HEVC, AAC, AC-3, Opus and FLAC, SRT, ASS with fonts, PGS (one without compression) and VobSub, chapters, global and track tags, IETF languages, names, flags, HDR colour, JPEG and PNG cover art — made by `dev/make_fixtures.py`, with a snapshot of what optimizing them gives. The tests compare against it, and the image's build runs them inside the image, with its own MKVToolNix and ffmpeg: if an update of the tools places or changes something differently, the build fails before the image is published.

Things to know: snapshots keep the old copy of every rewritten file until they expire; replication sends each one again; Plex re-analyses each changed file.

### Metrics: is it actually helping?

- A report card for today, the last 7 days, 30 days or 12 months:
  - **Skips served from cache** — jumps of more than 30 seconds that landed in cached data: read by Now Playing Cache, a whole file that was cached (Whole File Cache, or an earlier play), or a jump back into the cached lead-in.
  - **Fully cached age** — of everything read again, the age up to which it was all still cached.
  - **Plays started from cache** — of everything played, how much started from a lead-in (or whole file) already cached, by warm-up, Prefetch or an earlier play.
- An "Over Time" chart for each measure (by hour, day or month, with a table view): skips, data cached ahead, disk load, and **still cached 30 min later** — half an hour after each read into RAM, eight 1 MiB reads across it are timed; back within 4 ms means it came from cache (RAM, or the SSD if it moved there), since a hard drive takes longer just to reach the data. Reads on their way to the SSD aren't checked here; the next-day check after each warm-up covers the SSD.
  - **How Long Cached Data Lasts** — every time something cached is read again, the read is timed, so it says whether what was cached that long ago was still there. Added up by age, in RAM and on the SSD apart, that's how long cached data really lasts on your NAS, and the app suggests cooldowns from it. Ages count from the last time the app read that data, as the cooldown does; RAM reads from before a reboot are left out. A short cooldown (down to none) collects data fastest; the write history is kept for 6 months, across restarts.
  - **Data cached ahead** — what Now Playing Cache and Prefetch read into RAM for viewers, and how much of it was in cache already (each 32 MiB is timed); Prefetch's background reads to the SSD are shown separately.
- A "Needs Attention" list that names the cause and the setting to change.
- RAM-limit use, how busy the disks were while people watched, what's playing and being cached now, warm-up runs and a live event log. History is kept for a year.

### Easy to set up and live with

- **Sign In with Plex** — no token hunting. Plex and TrueNAS addresses are filled in when they run on the same NAS.
- **L2ARC Sizing Estimator** — how much cache the lead-in of everything in your libraries takes, in RAM without an L2ARC and on the SSD with one, counted in whole records as ZFS caches them. Four columns per library: *Target minimum* (the first record of each file at the recommended record size, indexes at the front), *Your minimum* (the first record at your record size, plus the index for files keeping it at the end), *Target* (the recommended record size, indexes at the front, at the lengths on the sliders) and *Your library* (the block sizes your files are written with now, at your settings). Below them: the system buffer (room for everything else ZFS caches; the larger it is, the longer cached files stay on the SSD) and the RAM the L2ARC uses to keep track of what it holds. Warm-up, Prefetch and Now Playing Cache read in whole records of each library's dataset, as ZFS does. Warm-up never caches less than a library's minimum: when the L2ARC is too small it shortens every lead-in by the same share, as little as fits, down to one record. A lead-in slider all the way down is one record too, on the Caching page and in the estimator; the estimator's sliders start from the default lengths. Leave room on top for how much your libraries will grow.
- **Disk speed benchmark** per dataset, so cache hits and preload timing are judged against your actual disks.
- Help behind small ⓘ buttons instead of walls of text, a ↺ to put any setting back to its default, changes saved as you go, dark mode, and a layout that works on a phone.
- **MQTT, for Home Assistant and more** (optional) — publishes health, streams, RAM in use, ARC and L2ARC, warm-up progress, the Metrics figures and lifetime totals, and takes commands. In Home Assistant a "Plex Cache" device appears on its own with 60–80 entities, including switches, buttons and sliders; Node-RED, openHAB and other MQTT tools can use the same topics. Status lights show each step of the connection. Follows the MQTT 3.1.1 and Home Assistant discovery standards, checked by its tests ([Standards](#standards)). See [MQTT](#mqtt-home-assistant-node-red-and-more).
- **Sign-in** for the web UI — a username and password set in the app's YAML (on by default; the example password is refused) — and **local network only**: devices outside your network are refused (System → Access).
- **Update notices** — checks GitHub every 6 hours (can be switched off in System) and says when there's a newer version, in the web UI and in Home Assistant.
- **Safe by design** — runs as TrueNAS's unprivileged `apps` user in a read-only container, with media mounted read-only and all extra permissions dropped; it writes only to its settings folder. Pure Python with no third-party dependencies. The only part that writes media is the optional [optimizer](#the-optimizer-files-written-for-caching), a second container that acts only when you ask it to. If its settings folder isn't writable it says how to fix it, rather than restarting endlessly.

## Install on TrueNAS

TrueNAS doesn't support third-party app catalogs since 24.10, so this installs as a custom app.

1. **Create a dataset for settings**, e.g. `tank/apps/plex-cache`, and give the `apps` user (568) read/write access.
2. **Find your Plex app's media mounts.** In Apps → Plex → Edit, note each *host path* and the *mount path* inside the container (for example `/mnt/tank/plexfiles` → `/data`).
3. **Apps → Discover Apps → ⋮ → Install via YAML**, name it `plex-cache`, and paste [`compose.yaml`](compose.yaml). Change the lines marked `CHANGE ME`:
   - the settings dataset → `/config`
   - each media host path → **the same mount path Plex uses**, read-only. Add a line per mount if Plex has several.
   - for the optimizer (the second service, optional): the same settings folder, read-only, and the media it may rewrite, writable. That's all: it finds the app's token in the settings folder, and it can only change files under the media folders you mount into it — leave out any you don't want changed (or the whole service). It runs as user 568; files it can't write, or whose owner it can't keep, are skipped (see the comments in the YAML for media owned by another user). If you add it later, the Optimizer page shows the lines to paste, filled in for your NAS.
   - `PLEXCACHE_PASSWORD` (and the username, if you like) → your own; the example password is refused. See [the web UI login](#the-web-ui-login).
4. Open `http://<your-nas-ip>:8642` and sign in.
5. Open **System**. If Plex and TrueNAS run on the same NAS, their addresses are filled in for you; otherwise enter your NAS's IP (Plex's port 32400 is added automatically). Choose **Sign In with Plex** — Plex only shares library and playback details with apps that hold a token. Optionally add a TrueNAS API key (user menu → API Keys) so Health can see your cache devices and dataset settings. The app only reads from the API. Status lights on the page show what's working.
6. If a library shows as not found, either mount it at the same path Plex uses, or mount it anywhere and pick the folder under **System → Media Mappings**. Folders that contain the library's files are marked ✓.
7. Check **Health** — it should say “Everything is OK” — then switch features on in **Caching**. If the media pool has no SSD cache (L2ARC), see **SSD Cache**.

### The web UI login

The web UI asks for a username and password, set under `environment:` in the app's YAML (Apps → plex-cache → Edit):

```yaml
      PLEXCACHE_USERNAME: plex-cache
      PLEXCACHE_PASSWORD: "something-long"
```

The example password in `compose.yaml` (`change-me`) is never accepted — anyone can read it here — so set your own when you install. Signing in with it explains what to change. The sign-in page's ⓘ button says where to find and change these settings.

To turn sign-in off, put a `#` in front of both lines (or remove them). The web UI then opens without a password, for anyone on your network; Health notes it, and warns if **Local network only** is off too.

The browser stays signed in for 30 days (a signed, HttpOnly cookie; the signing key lives in the config folder). **Sign out** ends that session on the server too, so a copied cookie stops working, and changing the password signs everyone out. Wrong passwords are answered one at a time, a second apart (guessing in parallel is no faster), and logged under Metrics → Recent Events; after 10 wrong passwords from one device, it's refused for 15 minutes. Behind a reverse proxy that sends `X-Forwarded-Proto: https`, the cookie is marked Secure. Scripts can use HTTP Basic auth. `/healthz` stays open so TrueNAS can check the app is up.

### Who can reach it

**Local network only** (System → Access, on by default) answers only devices on your network: private addresses (10.x, 172.16–31.x, 192.168.x), the NAS itself, link-local and IPv6 local addresses, and VPNs into your network with their own range, such as Tailscale (100.64–127.x). Anything else gets a page saying why, signed in or not. Behind a reverse proxy, the proxy's address is what counts. It can only be turned off from a device on your network.

Without a sign-in, the app also only answers to its IP address, `localhost` or a local name (`nas.local`, `truenas`), so a web page elsewhere can't reach it through a look-alike name (DNS rebinding). Using another name, set `PLEXCACHE_URL` to it, or turn sign-in on.

Off until you switch it on in **System → MQTT**. MQTT is the common language of home-automation and monitoring tools: everything connects to a *broker*, which passes messages along. Plex Cache connects to your broker as a client.

### Standards

Plex Cache's MQTT follows the published standards, and its tests check each rule, so an update can't quietly break them:

- **[MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html) (OASIS)** — the client rules for connecting (the login fields in the right order, a last will, a client ID of letters and digits that every broker accepts), topic names and filters (no wildcards when publishing, `#` and `+` only as whole levels, valid UTF-8, no null characters, 65,535 bytes at most), answering each QoS as the standard says, keep-alive pings, and a clean disconnect. A broker that breaks the rules (a malformed message, say) is disconnected from, as the standard requires.
- **[Home Assistant MQTT discovery](https://www.home-assistant.io/integrations/mqtt/)** — every discovery message names its software (`origin`), has a unique ID and a device, suggests its entity ID with `default_entity_id`, uses topic IDs Home Assistant allows, and reports availability with a last will; sensors pair device classes, units and state classes the way Home Assistant expects; controls have command topics; entities that go away are removed (an empty retained message); and when Home Assistant restarts (its `homeassistant/status` birth message) everything is announced again.

## How it works

Plex doesn't read a whole file at once — it buffers a little ahead of playback and reads more as needed. The disk delays you feel are seeks: starting a title, skipping, moving to the next episode. Plex Cache reads those parts *before* Plex asks for them, so ZFS already has them in RAM or on SSD.

- Bitrates come from Plex per file (or are calculated from size and duration when Plex has none), so a 4K remux gets more bytes cached than a 720p episode for the same number of seconds.
- Caching that needs an L2ARC is paced (by default 10% of disk time) and pauses for anything more important (see L2ARC Cache Settings above). "Run Now" runs at full speed and ignores the busy-disks pause, but still steps aside for buffering, Now Playing Cache and Prefetch reads, and scrubs.
- **Disk Speed** (System) is measured per dataset by *Benchmark Now*, which times reads of a few media files on each one. A read counts as "already cached" when it runs at least 4× faster than its dataset's speed. Unreadable files are reported, never counted as hits.
- L2ARC fills gradually and is evicted over time, which is why warm-up runs on a schedule. Size your L2ARC larger than the estimate so cached data lasts longer — even a modest SSD helps.

## Requirements

**Where it runs.** Plex Cache is written for TrueNAS SCALE, and that's where every feature works. It also runs on any Linux host with Docker and ZFS, with a smaller feature set: datasets are read from ZFS directly, and what needs the TrueNAS API — cache devices, pool layout, scrubs and resilvers, restarting the app — is left out. The System page says which it has found: TrueNAS for certain from its kernel (TrueNAS builds its own, named `…+truenas`, and every app runs on it), from the API (which adds the version), or from the host's `/etc/version` mounted into the app (`/host/etc/version`, read-only); `PLEXCACHE_PLATFORM=truenas` or `linux` says so by hand; otherwise "TrueNAS not detected". On TrueNAS without an API key, Health asks for one — it's what lets Plex Cache check cache devices and dataset settings, pause for scrubs, and install updates from the page — and an update that's waiting says so too. TrueNAS renames API methods between releases (`zfs.snapshot.*` became `pool.snapshot.*` in 25.04; `zfs.dataset.*` went in 25.10), so the app keeps each call's names over the versions (`plexcache/truenas.py`, `METHODS`) and uses the first the connected TrueNAS knows. Two guards go with it: when TrueNAS is connected, every call is checked against what that release offers (`core.get_methods`), and an **API compatibility** light on System → TrueNAS (and Health → TrueNAS API) says which, if any, it hasn't got — by what the call is for and the names tried — before the feature is used, asking you to report an orange light so the app can learn the new name; and every week a workflow (`dev/truenas_api.py`) reads the middleware's source on GitHub, the branch that becomes the next release, and fails when a call has no name left there, so a rename shows up before the release reaches anyone's NAS.

- TrueNAS SCALE / Community Edition 24.10 or later (Docker-based apps)
- Plex Media Server reachable from the NAS
- `primarycache=all` on each media dataset for any feature to work there: ZFS only fills L2ARC from data that passed through RAM, so `primarycache=metadata` means nothing gets cached (the old scripts recommended that — it doesn't work)
- For warm-up (and Prefetch's L2ARC-only choices): at least one cache (L2ARC) device on the media pool, and `secondarycache=all` on the media dataset
- A `recordsize` that suits each library's media, by its average bitrate: `512K` under 1 Mbps, `1M` up to 15 Mbps, `2M` up to 40 Mbps, `4M` above (Health → Libraries shows the recommended size and the second best for each). A new record size only applies to files written afterwards, so Health also checks every file and warns when any don't match it.

### Rewriting files after a record size change

The optimizer does this for you: **Optimizer → TrueNAS compression & record size** writes each file again so it takes the dataset's current record size and compression.

Without the optimizer, `plexcache/tools/rewrite_blocks.py` does the same from the TrueNAS shell: it copies files that were written with smaller blocks, one at a time, and swaps each one in place. It runs as root, so fetch it over HTTPS from the release you have installed (replace the version):

```sh
curl -fsSLO https://raw.githubusercontent.com/drsassafras/TrueNAS-Plex-Caching/v0.16.0/plexcache/tools/rewrite_blocks.py
sudo python3 rewrite_blocks.py tank/plexfiles            # look only
sudo python3 rewrite_blocks.py tank/plexfiles --apply    # rewrite
```

It paces itself (`--mb-per-sec`, default 80), skips files any program has open, copies with plain reads and writes so ZFS block cloning can't reuse the old blocks, checks each copy byte for byte, keeps owners, permissions, timestamps and ACLs, swaps with an atomic rename, leaves hard-linked files alone, and stops before free space runs low. It can be stopped and run again. Snapshots keep the old blocks until they expire, and replication will send rewritten files again.

**Long lists** (the Library page's files, a job's files on Processes) come a page at a time, and the pages are named by what they hold — "A–Be", "Bf–Da" — the first and last entry on each cut to what tells it from its neighbours, so you open the page you want rather than pressing Next. Every page is the same box, the one you're on framed; when more pages exist than fit, Beginning and End reach the rest. How many entries make a page is yours to set in System → Preferences: *Entries per Library page* (200 to begin with) for these, and *Entries per Tools page* (40) for the cards on the tools' pages, the Optimizer's and the check pages. Titles sort by their letters: an opening quote, apostrophe or bracket doesn't count, so *'Twas the Night Before Christmas* sits with the Ts.

## Development

**Branches and versions.** `main` is what's released: each push to it is tagged and built as the `:latest` image, shown as a plain version (0.16.0). `dev` is where work lands between releases; every push to it is built as the `:dev` image, with the last number of the version raised each time (0.16.1, 0.16.2…) and `-dev` appended on the page (0.16.2-dev). The two never cross: a dev install updates on new dev builds, a stable install on releases. The channel comes from the build (the Dockerfile's `PLEXCACHE_CHANNEL` and `PLEXCACHE_COMMIT` arguments, set by the workflow), and the update check follows it, only ever offering a build that exists: it asks GitHub for the branch's newest finished build (its last successful workflow run) and reads the version at that commit, so a push still building isn't offered; a dev build also compares the commit, the number being the same between pushes it hasn't bumped. **Check Now** on the System page asks GitHub straight away; the app also checks a few seconds after it starts. With the TrueNAS API connected (a key allowed to manage apps), **Update Now** — on the System page and under the version in the menu — has TrueNAS pull the newer image and restart the app; TrueNAS itself only flags updates for catalogue apps, so a custom app on a tag like `:dev` or `:latest` never shows one there. The version in the menu links to this build on GitHub: its release, or for a dev build its commit. (A development install that mounts the source folder over `/app/plexcache`, as `dev/compose.dev.yaml` does for `tnsync`, runs that folder's code whatever image it pulls: it updates when the folder does.)

The tests draw every page the way the browser does — `tests/render.js` runs `app.js` in node with a stand-in for the DOM, from one `/api/state` answer — so they can read what a page says in a given state. One test draws every page from a fresh app's state, before the first checks have run, and fails if any place gives a verdict ("TrueNAS not detected", "No library…", "RAM only — couldn't check") rather than saying it's checking; then runs the checks and makes sure the Checking… texts have gone.

**Shared code, no exemptions.** Every tool page is built on the shared tool page and every check tool on the shared check page, and the tests hold them there. No page, tool or check is exempted from the shared code or a standard test (added to a test's list of exceptions, or a rule loosened to let it pass) without the maintainer's express permission: see [`CLAUDE.md`](CLAUDE.md).

To try changes on your own TrueNAS before pushing, see [`dev/README.md`](dev/README.md): a test copy of the app plus `tnsync`, which runs the tests, copies your code to the NAS and restarts the test app in one command.

```sh

python3 dev/coverage.py   # the same, with test coverage per file (Python 3.12+)
python3 tests/demo.py     # UI demo at http://127.0.0.1:8642 with sample data
node dev/screenshots.js   # README screenshots (see the file for how to run it)
node tests/render.js system < state.json   # a page as the browser draws it from one /api/state answer (the tests use it)

```

### Translations

Each language has a catalog in `plexcache/web/i18n/<code>.json`, keyed by the English text. Texts are marked in the code with `T()`, `H()`, `P()` and `N()` in JavaScript, `data-i18n` attributes in HTML and `M()` in Python. You translate in place: a text with no translation yet is in the catalog as `null`, and the app shows the English until it's filled in.

**When to translate:** only when a release is being made, and only when the maintainer asks for the release. Day to day, a change that adds or changes texts leaves the catalogs alone: a new text isn't in them yet (the app shows the English) and an old one lingers until the release. Making the release, run `python3 dev/i18n.py sync` to bring every catalog in step (new texts as `null`, unused ones dropped), then translate.

```sh
python3 dev/i18n.py status      # how much of each language is translated
python3 dev/i18n.py sync        # for a release: add new texts as null, drop unused ones
python3 dev/i18n.py check       # placeholders, HTML tags and plural forms match the English
python3 dev/i18n.py check --release   # ...and every catalog in step with the code
python3 dev/i18n.py leftovers   # English in app.js that isn't marked for translation
```

Keep every `{placeholder}` and HTML tag from the English. A plural is an object with the forms its language uses, e.g. `{"one": "{n} file", "other": "{n} files"}`; Russian, Ukrainian and Polish also use `few` and `many`, and Japanese, Korean and Chinese only `other`. `en-US.json` and `en-GB.json` only list the texts whose spelling differs from the Canadian original. The tests always fail if a translation doesn't match its English. They fail on a catalog out of step with the code only for a release: with `PLEXCACHE_I18N_RELEASE=1`, which CI sets for `main`, version tags and pull requests into `main`, or under `tnsync release` / `tnsync beta`.

#### Writing the texts

The English is the original (Canadian spelling), so it sets the style for every language:

- **Title Case** for what names a place or an action: page and card titles, and buttons (*Optimize Now*, *Re-run All Checks*, *Media Mappings*). Articles, short conjunctions and prepositions stay lowercase inside (*Convert Folder to Child Dataset*). The features' names are always capitalized: Now Playing Cache, Lead-in Cache, Whole File Cache, Prefetch.
- **Sentence case** for everything else: sub-headings inside a card, field and checkbox labels, choices in a list, column headers, badges, status lines and help.
- Refer to a page or card by its title (*System → Media Mappings*), and to a button or choice in quotes or bold, exactly as it reads.
- Typographic apostrophes and quotes (’ “ ”), and *the L2ARC* (an L2ARC, the SSD cache) in a sentence.
- Say a thing once per screen: a card's hint, its ⓘ and the status line under it shouldn't repeat each other, and a summary doesn't repeat the numbers shown right under it.

| `PLEXCACHE_CONFIG` | settings folder (default `/config`) |
| `PLEXCACHE_PORT`, `PLEXCACHE_HOST` | where the web UI listens (default `8642` on all addresses) |
| `PLEXCACHE_DEBUG` | any value: more detail in the app's log |
| `PLEXCACHE_OPTIMIZER_URL` | where the optimizer service is (default `http://plex-cache-optimizer:8643`, the second service in the YAML) |
| `PLEXCACHE_OPTIMIZER_TOKEN` | the secret the app and the optimizer share. Not needed: the app makes one and keeps it in its settings folder (`optimizer-token`), and the optimizer reads it there (`/config/optimizer-token`, mounted read-only). Set the same value in both services to use your own |
| `PLEXCACHE_MEDIA_ROOTS` | optimizer only: the folders it may write. Not needed: by default, the folders mounted into it writable |
| `PLEXCACHE_OPTIMIZER_PORT` | optimizer only: the port it listens on inside the app (default `8643`) |
| `PLEXCACHE_TOOLS_PATH` | extra folders to find MKVToolNix, ffmpeg, oxipng and jpegtran in (e.g. the macOS app bundle when testing) |
| `PLEX_URL`, `PLEX_TOKEN`, `TRUENAS_URL`, `TRUENAS_API_KEY` | fill in those settings when they're empty (handy for scripted installs); the web UI can change them afterwards |
| `TZ` | time zone for schedules |

### The config folder

`settings.json` (all settings, including the Plex token, TrueNAS API key and MQTT password — readable only by the app), `history.json` (Metrics history), `session.key` and `signed-out.json` (web UI sessions), and small files remembering the web UI's address, a folder being moved to its own dataset (`migration.json`), the file job running now and the last one that ended (`job.json`, `job-last.json`), the job log (`job-log.jsonl`, six months), the Home Assistant entities published, the token the optimizer accepts (`optimizer-token`), this system's ID in claims (`instance-id`), the link to the other Plex Cache (`peer-key.json`, this side's key pair, readable only by the app; `peer.json`, the pairing), when each library's marker was first written (`published.json`), Mirror Checks' last comparison of each library (`mirrorhealth.json`; what's ignored is kept with Library Health's, in `health-ignored.json`), the ZFS record (`zfs-record.json`: each dataset's settings since when, and each file's compression), and what each file's optimizer tag says (`optimized.json`, with its size, modification time and inode, and the SHA-256 of the file the optimizer left). `GET /api/export` downloads the settings without any secrets.
